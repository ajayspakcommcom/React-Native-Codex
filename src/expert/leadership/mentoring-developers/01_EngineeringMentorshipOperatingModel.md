# Engineering Mentorship Operating Model

## Objective
- Grow engineers deliberately instead of relying on random experience accumulation.
- Create repeatable support for technical depth, ownership, and decision quality.

## Mentorship is not one thing
- coaching
  - helps a developer think better and solve problems independently
- teaching
  - transfers specific knowledge or techniques
- sponsorship
  - creates opportunities, visibility, and stretch scope
- feedback
  - clarifies the gap between current and expected performance

## Enterprise mentorship model
### Junior engineers
- strengthen fundamentals
- improve debugging and communication
- learn how to break work into safe increments

### Mid-level engineers
- improve system thinking
- take ownership of features end-to-end
- learn trade-off reasoning and review quality

### Senior engineers
- improve architecture judgment
- mentor others deliberately
- raise team-wide engineering standards

## Operating cadence
- weekly or biweekly one-on-ones for active growth work
- written growth goals for the quarter
- concrete examples tied to real project work
- periodic recalibration between mentor, mentee, and manager

## Good mentorship behaviors
- ask for reasoning before giving answers
- assign work that stretches, but does not drown
- review decisions, not only code syntax
- make feedback specific, observable, and timely
- distinguish “this was wrong” from “this was incomplete”

## Failure modes
- advice without context
- vague encouragement with no action path
- turning mentorship into micromanagement
- protecting someone from all difficult work
- confusing sponsorship with favoritism
